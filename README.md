# Flow of Money

**Flow of Money**는 국제 금융 인프라를 한글·영문으로 탐색하는 인터랙티브 웹 애플리케이션입니다. 메시징, 승인, 청산, 결제, 자산 이전을 같은 것으로 취급하지 않고 각 단계와 참여자를 분리해 보여 줍니다. 지도 위 연결선은 개별 거래나 실제 자금 이동을 재현한 것이 아니라, 출처로 뒷받침되는 금융 시스템의 구조를 설명하는 도식입니다.

## 대상과 범위

이 프로젝트는 금융 인프라를 학습·비교하기 위한 제품입니다. 투자 조언, 실시간 시장 데이터, 결제 지시 또는 거래 원장으로 사용할 수 없습니다.

현재 다루는 네트워크와 관점은 다음과 같습니다.

| 영역 | 화면에서 설명하는 것 | 혼동하면 안 되는 점 |
| --- | --- | --- |
| SWIFT | 은행 간 금융 메시징 | 메시지 전송 자체가 자금 결제는 아닙니다. |
| Visa | 카드 승인, 청산, 결제의 구분 | 카드 네트워크 처리량은 개별 발급사·가맹점의 원장이 아닙니다. |
| CHIPS · Fedwire | 미국 달러 고액 결제 경로 | 두 시스템은 서로 다른 운영·결제 경로입니다. |
| 채권 발행 | 발행사, IB, 예탁결제 등 1차 시장의 흐름 | `issuance`는 유통시장 결제와 별개의 의미입니다. |
| OTC 파생상품 | 계약, 담보 관리, 청산 | BIS 집계 통계와 운영 관행을 설명하며 개별 포지션을 표시하지 않습니다. |
| Circle USDC | 발행, 상환, 온체인 자산 이전 | 지원 네트워크와 유통량은 시점 의존적입니다. |

## 빠른 시작

필수 환경은 Node.js와 npm입니다. 저장소에는 `package-lock.json`이 있으므로 CI 또는 재현 가능한 설치에는 `npm ci`를 권장합니다.

```bash
npm ci
npm run dev
```

개발 서버는 기본적으로 `http://127.0.0.1:4173`에서 실행됩니다. 다른 기기에서 확인해야 하면 Vite가 바인딩한 호스트 주소를 사용합니다.

```bash
npm run build
npm run preview
```

`build`는 TypeScript 컴파일과 데이터 계약 검증을 포함합니다. 따라서 배포 전에는 별도로 `data:validate`를 실행하지 않아도 되지만, 데이터만 수정했다면 해당 검증을 먼저 빠르게 실행할 수 있습니다.

## 화면과 URL

앱은 브라우저 History API 기반의 SPA이며, 기본 진입 경로는 `/ko/map`입니다. `/en`을 사용하면 같은 화면을 영어로 제공합니다. 알 수 없는 경로는 해당 언어의 지도 화면으로 이동합니다.

| 경로 | 목적 |
| --- | --- |
| `/{locale}/map` | 지도, 필터, 상세 패널 및 학습용 타임라인 |
| `/{locale}/networks[/slug]` | 네트워크 설명과 세부 항목 |
| `/{locale}/institutions` | 금융 인프라 참여 기관의 역할 |
| `/{locale}/assets[/slug]` | 자산 관점의 설명 |
| `/{locale}/learn[/slug]` | 프로젝트 소개와 학습 콘텐츠 |
| `/{locale}/data` | 버전, 커버리지 고지, 지표 및 원문 출처 |

언어 전환은 현재 경로와 URL 검색 매개변수를 보존합니다. 지도에서 선택한 뷰는 URL로 공유할 수 있도록 설계되어 있으므로, 새 상태를 추가할 때에도 링크 재현성을 유지해야 합니다.

`{locale}`에는 `ko` 또는 `en`을 사용합니다.

## 데이터 모델과 갱신 절차

정적 데이터는 `public/data/`에 있고, 브라우저는 다음 세 파일을 병렬로 가져옵니다.

| 파일 | 책임 |
| --- | --- |
| `manifest.json` | 스냅샷 버전, 생성 시각, 사용자에게 보이는 커버리지 고지 |
| `sources.json` | 모든 공식 원문 출처의 식별자, 제공기관, URL, 발행·검색 시각, 대상 기간, 갱신 주기 |
| `metrics.json` | 화면 지표의 값·표시 형식·언어별 레이블·네트워크·출처 연결 |

지도 노드, 도식 경로, 네트워크 정의는 `src/data.ts`에 있습니다. 모든 경로는 `representation: "schematic"`이며, 각 경로에는 근거가 되는 `sourceIds`가 있어야 합니다. 실제 거래 위치·실시간 거래·고객 데이터는 넣지 않습니다.

데이터를 갱신할 때는 다음 순서를 사용합니다.

1. 공식 제공기관의 원문을 확인하고 `sources.json`에 HTTPS URL과 정확한 메타데이터를 기록합니다.
2. 새 출처의 `id`를 `metrics.json`의 `sourceId` 또는 `src/data.ts` 경로의 `sourceIds`로 연결합니다.
3. `manifest.version`을 `YYYY.MM.DD` 형식으로, `generatedAt`을 새 스냅샷 시각으로 갱신합니다.
4. `npm run data:validate`를 실행하고, 사용자에게 보이는 표시값·대상 기간·통화/단위를 다시 확인합니다.

검증기는 빈 배열, 중복 ID/URL, 비 HTTPS URL, 잘못된 날짜, 발행일보다 이른 검색일, 스냅샷 생성일보다 늦은 검색일, 미등록 네트워크, 중복 지표 ID, 빈 표시 레이블, 숫자가 아닌 값, 끊어진 출처 참조를 거부합니다. 출처를 추가하거나 날짜를 바꾸면 반드시 `manifest.generatedAt`과의 시간 관계도 확인해야 합니다.

## 개발 규칙

- 금융 용어의 의미를 보존합니다. 특히 메시징·승인·청산·결제·발행·자산 이전은 서로 바꿔 쓰지 않습니다.
- UI에서 수치나 출처를 보일 때는 `public/data`의 스냅샷을 단일 진실 공급원으로 사용합니다. 코드에 같은 숫자를 중복 하드코딩하지 않습니다.
- 한국어와 영어의 레이블을 함께 갱신합니다. 언어 전환, 직접 URL 진입, 뒤로/앞으로 탐색도 확인합니다.
- 키보드, 화면 읽기 도구, 좁은 화면을 동등한 사용 경로로 취급합니다. 시각적으로 숨긴 제어는 포커스 가능 여부와 ARIA 의미를 유지해야 합니다.
- 지도 렌더러는 큰 의존성입니다. MapLibre와 Deck 관련 변경은 기존 청크 분할을 유지하고, 필요하지 않은 초기 번들 로딩을 피합니다.

## 검증

변경 범위에 맞춰 아래 순서로 실행합니다.

```bash
npm run data:validate
npm test
CI=1 npm run test:e2e
npm run build
```

`npm test`는 데이터·컴포넌트 단위 테스트를 실행합니다. `npm run test:e2e`는 Playwright로 데스크톱 Chrome(1440×900)과 Pixel 7(390×844)을 모두 검사합니다. CI 환경에서는 새 개발 서버를 시작하도록 구성되어 있으므로, 릴리스 판단에는 위와 같이 `CI=1`을 사용합니다.

## 배포

Cloudflare Pages 기준 설정은 다음과 같습니다.

| 설정 | 값 |
| --- | --- |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Node package manager | npm (`package-lock.json` 사용) |

`public/_redirects`는 모든 경로를 `index.html`로 전달하므로 `/en/data`처럼 직접 진입한 SPA 경로도 동작합니다. 배포 후에는 최소한 한국어·영어 지도, 데이터 페이지 직접 URL, 모바일 메뉴, 출처 링크를 확인합니다.

## 프로젝트 구조

```text
src/
  App.tsx                 경로 해석, 언어 전환, 전역 헤더
  components/             지도, 타임라인, 필터, 상세·정보·데이터 화면
  data.ts                 네트워크·도식 노드·경로 정의와 데이터 로더
  router.ts                History API 기반 클라이언트 라우터
  types.ts                 데이터 계약 타입
public/data/              배포되는 출처 기반 스냅샷
scripts/validate-data.mjs 데이터 계약 검증기
tests/                    Playwright 사용자 흐름 테스트
```

## 기여 흐름

작은 단위로 브랜치를 만들고, 데이터·UI·문서 변경을 함께 검토합니다. PR에는 변경 내용, 데이터 또는 동작상 이유, 사용자 영향, 실행한 검증을 적습니다. 출처 변경 PR에는 새 원문 URL, 대상 기간, 스냅샷 날짜를 반드시 포함해야 리뷰어가 수치의 시점을 판단할 수 있습니다.
